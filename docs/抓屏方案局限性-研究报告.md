# 抓屏方案（Windows Graphics Capture）局限性 · 研究报告

> 研究日期：2026-09-27
> 对应版本：v1.0.7（`windows-capture` 2.0.1）
> 前置材料：`docs/抓屏局限性-交接材料.md`
> 研究纪律：所有外部结论均附来源；本机实测与「用户环境推论」严格分开标注。

---

## 零、一句话结论

当前抓屏方案的硬门槛**不是驱动、不是显卡品牌，而是「窗口必须真的被 DWM 渲染」**：
只要窗口可见、且系统是 Win10 1809+ 的常规桌面显卡环境，它就能跑；
一旦窗口处于**最小化 / 无渲染内容 / 虚拟机-远程桌面无硬件 D3D11 设备**的状态，
它会**静默地一帧都不送**——`start_free_threaded()` 正常返回、不抛异常、`stop()` 也不报错，
调用方只能靠「等不到帧」自己判死。**这是本方案最大的风险点，也是自检应该优先覆盖的地方。**

替代方案方面：`windows-capture` 2.0.1 自带一条 **DXGI Desktop Duplication** 后路（同库、零新增依赖），
但它**只能抓显示器、不能抓单个窗口**，且同样依赖 D3D11 硬件设备——**不是万能兜底**。
真正意义上的「无驱动、老系统也能用」的兜底是 **BitBlt / PrintWindow**（纯 GDI，系统自带），
代价是**会被遮挡、独占全屏/GPU 直绘窗口可能全黑**。

## 一、当前方案的硬性环境要求（逐条给依据）

### 1.1 系统版本

| 要求 | 值 | 依据 |
|---|---|---|
| API 存在 | `GraphicsCaptureSession` 自 **Win10 1803 (10.0.17134.0)** 引入 | [MS Learn: GraphicsCaptureSession](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession) — "Device family: Windows 10, version 1803 (introduced in 10.0.17134.0)" |
| 库自带的门槛 | `UniversalApiContract` **major ≥ 8** | 库源码 `graphics_capture_api.rs`：`ApiInformation::IsApiContractPresentByMajor(&HSTRING::from("Windows.Foundation.UniversalApiContract"), 8)` |
| 按 HWND 建 item | `IGraphicsCaptureItemInterop::CreateForWindow` 需 **Win10 1903+** | [trycua/cua `wgc.rs`](https://github.com/trycua/cua) 注释："Minimum OS: Windows 10 version 1903 (~April 2019)"；"`CreateForWindow` failed — requires Win10 1903+ and the target window must exist" |

**口径统一**：交接材料里写的「Win10 1809 (build 17763)」偏保守但安全。
本项目的抓取方式是**按 hwnd**（`GameWindowCapturor.py` L66 `WindowsCapture(window_hwnd=...)`），
因此实际生效的是 **1903** 这条更严的门槛。
不过 UniversalApiContract v8 与 1809 的对应关系在公开资料里表述不一，
**建议对外仍写「Win10 1809 以上」**（保守、不会漏掉能跑的用户），代码注释里标注 1903 这个更精确的说法。

### 1.2 显卡 / 驱动 / 虚拟机

| 项 | 要求 | 依据 |
|---|---|---|
| 需要能创建 **硬件 D3D11 设备**（FL 11.0 + BGRA 支持） | 必需 | `wgc.rs`：`D3D11CreateDevice(None, D3D_DRIVER_TYPE_HARDWARE, ..., D3D11_CREATE_DEVICE_BGRA_SUPPORT, Some(&[D3D_FEATURE_LEVEL_11_0]), ...)`，失败即 `.context("D3D11CreateDevice failed (hardware feature-level 11.0 + BGRA)")` |
| 显卡品牌 | **无关紧要**，只要提供 D3D11 FL11.0 即可 | [MS Learn D3D11CreateDevice](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-d3d11createdevice) — 默认 pAdapter=NULL 时用枚举到的第一个适配器；FL11.0 是 Win7 以来 D3D11 运行时的基线 |
| **不需要**安装任何抓屏驱动 | 已确认 | 交接材料 §二：本机实测无额外驱动拿到 2560×1440 帧；且库依赖仅 `numpy` + `opencv-python`（见 `requirements.txt` L2-3 与 PyPI `requires_dist`） |
| 虚拟机 | **无解**（若为 GPU-P / 虚拟显示适配器） | [luxstream-setup](https://github.com/VjekoslavDugec/luxstream-setup)："The paravirtual display adapter does not implement the Desktop Duplication API, so capture fails"——该仓库专门为 Hyper-V GPU-P 客户机打 WGC 补丁。`cua` 的注释也印证："Headless/virtualized Windows sessions can expose DWM but no WGC-compatible hardware device" |
| 远程桌面（RDP） | **高风险**，属同上「无硬件 D3D11 设备」类 | 同上 `cua/capture.rs` 注释（headless/virtualized 场景）。**注意：本机未能实测 RDP，此条为依据第三方源码注释的推断，需实机验证** |

### 1.3 目标窗口的要求

| 要求 | 说明 | 依据 |
|---|---|---|
| 窗口**不能最小化** | 最小化窗口没有渲染内容，WGC 抓不到 | `wgc.rs`：`bail!("WGC cannot capture a minimized window (no rendered content)...")`；本机实测见 §三 |
| 窗口**不能是独占全屏** | 必须窗口模式 | 交接材料 §三.2（项目已有记录）；WGC 走 DWM 合成帧，独占全屏绕开 DWM |
| 窗口尺寸须与配置一致 | 否则裁剪失败 | `src/ui/ui.py` L2675-2719（项目已加预检） |
| 窗口须真实渲染（非 cloaked） | item 尺寸为 0 即异常 | `wgc.rs`：`"WGC item size is {}x{} — target may be hidden/cloaked"` |

**被其它窗口挡住 → 不影响**（这是 WGC 相对 GDI 的核心优势）。
见 `cua/wgc.rs` 模块注释："WGC captures the window's own composited frames out of DWM regardless of z-order"。

## 二、失败场景清单（能自救 vs 无解）

### 2.1 用户能自救的

| 场景 | 现象 | 自救方法 | 项目侧现状 |
|---|---|---|---|
| 窗口被最小化 | 0 帧，无异常 | 还原窗口（右键任务栏 → 还原） | **已有预检**：`src/ui/ui.py` L2640-2665，`IsIconic` 检查 + 弹窗提示 ✅ |
| 窗口尺寸与配置不符 | 裁剪返回 None，0 帧 | 用「一键按当前窗口大小改配置」 | **已有预检**：`src/ui/ui.py` L2675-2719 ✅ |
| 游戏没切到前台 | 首帧抓到主界面 | 手动点游戏窗口再按 F4 | **已有预检**：`src/ui/ui.py` L2721-2759 ✅ |
| 游戏开了独占全屏 | 抓不到 | 改成**窗口模式** | 已有文档说明（README / 用户版） |
| 窗口标题被改/多候选歧义 | 抓错窗口（静默） | 手动指定窗口标题 | `GameWindowCapturor.py` L41-44 支持 `window_title` 参数 |

### 2.2 无解的（环境不满足，必须明确告知）

| 场景 | 判定 | 处置建议 |
|---|---|---|
| **系统低于 Win10 1809/1903** | 无解。`IsApiContractPresentByMajor(..., 8)` 返回 false → 库抛 `Error::Unsupported`（消息 "The Graphics Capture API is not supported on this platform."） | 明确告知系统版本不足，无法支持。**注意**：这条会在 `start_free_threaded()` 时抛异常→可检测 ✅ |
| **虚拟机（虚拟显示适配器 / GPU-P）** | 无解（除非宿主正确透传硬件 GPU） | 明确告知「本项目不支持在虚拟机内运行」。**这正是 README 声明不支持虚拟机但没写原因的答案**——见 §五 |
| **远程桌面会话** | 高风险，大概率无解（依据第三方源码推断，**未实机复现**） | 建议加检测并提示「请在本地物理显示器前运行」。**注意**：即使 RDP 下 WGC 失败，若是在本机 RDP 连本机、或已断开重连，行为可能有差异，需实测 |
| **无硬件 D3D11 设备**（老核显 / 无显卡驱动 / 驱动异常） | 无解 | 明确告知更新显卡驱动或换机 |
| **独占全屏游戏** | 无解（WGC 架构性限制） | 已有文档说明，要求窗口模式 |
| **游戏窗口本身不渲染**（黑屏/未初始化完） | 无法用 WGC 解决 | 提示等待游戏加载完成 |

## 三、失败时的错误行为（实测证据 — 本章最重要）

### 3.1 本机实测（开发机 Win11 build 26200，RTX 3070）

用 `_tmp/probe_modes.py` 对同一个真实窗口（tkinter 窗口，hwnd=7343460）做对照：

```
=== A: restore/visible ===
   start_free_threaded RETURNED OK
   frames in 4s: 1
   stop() ok
=== B: MINIMIZED ===
   start_free_threaded RETURNED OK
   frames in 4s: 0          ← 静默失败：不抛异常、不回调 on_closed
   stop() ok
```

用无效 hwnd（99999999）实测：

```
=== T1: bogus hwnd (99999999) ===
   start raised: Exception Capture session threw an exception:
                 Failed to convert item to `GraphicsCaptureItem`
```

### 3.2 结论：库存在**两种截然不同的失败形态**

| 失败类型 | 表现 | 能否在启动时捕获 |
|---|---|---|
| **A 类：可抛异常** | 系统不支持、hwnd 无效、D3D11 设备创建失败 | ✅ `start_free_threaded()` 直接抛 `Exception`，可 try/except |
| **B 类：静默不送帧** | 窗口最小化、窗口被 cloaked、DWM 不合成该窗口 | ❌ **启动不报错、on_closed 不触发、stop() 不报错**，只能靠「等帧超时」判定 |

**B 类是最危险的**，正是交接材料里说的「静默失败最难查」。
项目现有实现（`GameWindowCapturor.py`）**没有等帧超时判定**——
`get_frame()` 在 `self.frame is None` 时返回 None，上游只能靠 UI 层刷「还没抓到游戏画面」。
`tools/grab_frame.py` L68-76 有 8 秒超时（开发工具，未打进用户包），
L71 的提示是「窗口最小化了？」——**做了但没覆盖全部 B 类成因**。

### 3.3 关于 `on_closed`

`on_closed` 只在**窗口被关闭**时触发（`GameWindowCapturor.py` L84-89 仅 `logger.warning`）。
它**不是失败信号**——最小化时实测不触发。不要把它当作「抓屏挂了」的判据。

## 四、能否提前检测 / 环境自检能做到什么程度

### 4.1 先说一个坏消息：库没把 `is_supported()` 暴露给 Python

**实测证据**（`_tmp/probe_api.py`）：

```
WindowsCapture: ['event', 'on_closed', 'on_frame_arrived', 'start', 'start_free_threaded']
NativeWindowsCapture: ['start', 'start_free_threaded']
```

Rust 侧 `GraphicsCaptureApi::is_supported()` 确实存在（源码有 `pub fn is_supported()`），
但 **Python 绑定没有把它导出**——`dir(windows_capture)` 里搜 `support` 返回 `[]`。
所以**不能直接调用「我这台机器支持吗」**，只能用间接手段。

### 4.2 能做的自检（按性价比排序）

**第一档：零成本、必做（不依赖库，纯 win32api / ctypes）**

| 检查 | 方法 | 结论 |
|---|---|---|
| 系统版本 | `ctypes.windll.ntdll.RtlGetVersion()`（**本机实测可用**：返回 `10.0.26200`） | < 1903 直接判不支持 |
| 窗口是否最小化 | `win32gui.IsIconic(hwnd)` | 已实现（L2651） |
| 窗口尺寸 vs 配置 | `win32gui.GetClientRect` | 已实现（L2690-2693） |
| 窗口是否 cloaked | `DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED=14)` | 未实现，可补 |
| 是否虚拟机 | 注册表/`GetSystemFirmwareTable` / 驱动名（`vboxguest`、`vmware`、`vmbus`） | 未实现，可补（启发式，非 100% 准） |
| 是否 RDP 会话 | `GetSystemMetrics(SM_REMOTESESSION)` | 未实现，可补（**这是最便宜有效的 RDP 检测**） |

**为什么 `RtlGetVersion` 而不是 `platform.version()`**：
后者会因程序清单（manifest）里的兼容性声明被 Windows 谎报——
PyInstaller 打包的程序尤其容易踩这个坑，读出的是 6.2（Win8）之类的假版本。

**第二档：低成本"真抓一次试试"（最可靠）**

纯采样式自检（探针窗口 + 读像素）**不适用于本场景**，
因为真正要验证的是「**游戏那个窗口**能不能被抓到」——
探针窗口能抓不代表游戏窗口能抓（游戏可能独占全屏、可能不渲染）。

⇒ **正确做法就是项目已有的路子**：在启动引擎/录制器前，
**按真实 hwnd 起一次捕获，起一个 3~5 秒的看门狗计时器**，
超时无帧就按 B 类失败处理，并**按上面的检查项逐条排除、给出具体原因**。
`tools/verify_no_frame_reason.py` 看名字就是干这个的，应确认它是否已覆盖这些分支。

**第三档：不值得做的**

- 直接调 `is_supported()`：库没暴露，除非改用 `ctypes` 手工查
  `Windows.Foundation.Metadata.ApiInformation` —— 可行但脆（依赖 WinRT COM 激活），**不建议**。
- 用 WARP（软件 D3D）替代硬件设备：WGC **要求硬件**；且即便能跑，软渲染抓屏性能极差。

### 4.3 自检能做到的程度（结论）

**能做到**：把「窗口最小化 / 尺寸不符 / 未前台 / 系统版本不足 / RDP / 虚拟机 / 无硬件 D3D11」
这几类**在开跑前就识别出来，并给出人话原因 + 具体操作**。

**做不到**：100% 预测。
因为 B 类失败（静默）的最终判据只能是「真抓一段时间看有没有帧」，
且**独占全屏、游戏未渲染完**这类与游戏自身状态相关的因素无法在开跑前静态判定。

⇒ 定位应是「**把 90% 的常见坑拦在前面**」，而不是「保证一定成功」。

## 五、几个具体问题的答复（交接材料 §四 待办）

### 5.1 `windows-capture` 2.0.1 的官方最低系统要求
见 §1.1。**库 README 未声明最低系统要求**（已逐字核对 [PyPI description](https://pypi.org/pypi/windows-capture/json) 与 [python README](https://github.com/NiiightmareXD/windows-capture/tree/main/windows-capture-python)）——
只有源码里的 `UniversalApiContract >= 8` 这一处可查。**这是库文档的缺失，不是我没查到。**

### 5.2 README 说「不支持虚拟机」的原因（原文档没写）
**基本可以确认与抓屏有关**：虚拟机的虚拟显示适配器通常**不实现 Desktop Duplication，
也不提供 WGC 可用的硬件 D3D11 设备**（依据见 §1.2 的 luxstream-setup 与 cua 注释）。
这是**抓屏侧的硬限制**，不是按键驱动侧的问题。

### 5.3 Unity 重制版客户端对 WGC 是否友好
**未找到「Unity 屏蔽 WGC」的证据。**
反方向证据：库的 issue 列表里有用户**成功**用 `window_name='MapleStory'` 抓过冒险岛
（[issue #189](https://github.com/NiiightmareXD/windows-capture/issues/189)，
报的是「重复帧」而非「抓不到」）。
⇒ **本项判定为：无证据表明 Unity 客户端屏蔽 WGC；交接材料里「有项目显式屏蔽该 API」的说法，
本次检索未能在本项目的目标客户端上得到证实。**

### 5.4 多屏 / 负坐标窗口是否有额外影响
**无影响（对按 hwnd 抓取这条路径）。**
理由：按 hwnd 抓取时，帧像素坐标是**相对窗口自身**的，
屏幕坐标是负值只影响「把游戏画面坐标换算成屏幕点击坐标」那一步
（`get_game_window_client_origin` → `ClientToScreen`），**与抓屏无关**。
`cua/capture.rs` 的测试用例里明确覆盖了负坐标：
`FrameGeometry::from_bounds((-100, 20, 300, 320))` —— 作者的注释也只是说
GetWindowRect 在负坐标下取值正常。
⇒ issue #2 用户的真正卡点**不是负坐标**，而是**窗口尺寸与配置不符**（项目已在 L2675 加了预检）。

### 5.5 2.0.1 有没有更好的抓取参数
有，且**项目当前没用的**：
`WindowsCapture.__init__` 支持 `draw_border` 和 `secondary_window`。
- `draw_border=False`：关掉 Windows 给被抓窗口画的**黄框**（Win11 才有 setter，老系统自动忽略）。
  `tools/grab_frame.py` L54 已经用了，但 **`GameWindowCapturor.py` L66 没用** —— **建议补上**（用户观感问题）。
- `secondary_window`：抓子窗口，本项目用不到。

⚠️ 注意 `GameWindowCapturor.__init__` 的**第一个位置参数是 `cursor_capture` 默认 `True`**
（实测签名：`(self, cursor_capture: bool | None = True, ...)`）。
本项目现在是 `WindowsCapture(window_hwnd=...)` 全用关键字，**避开了这个坑**，不要改成位置参数。

## 六、替代方案对比

### 6.1 候选总览

| 方案 | 依赖 | 抓单窗口 | 被遮挡时 | 独占全屏 | 老系统 | 需用户装东西 | 违反项目原则? |
|---|---|---|---|---|---|---|---|
| **A. 现有 WGC**（windows-capture） | 无（已在包内） | ✅ | ✅ **能抓** | ❌ | Win10 1809/1903+ | 否 | 否 |
| **B. 同库 DXGI Desktop Duplication** | **无**（同库自带，2.0.1 已导出 `DxgiDuplicationSession`） | ❌ **只能抓显示器** | ✅（抓整个屏幕） | 视情况 | Win8+ | 否 | 否 |
| **C. BitBlt（GDI 屏幕区域）** | 无（系统 API） | ⚠️ 实为抓屏幕区域 | ❌ **抓到遮挡物** | ❌ | **Win XP+** | 否 | 否 |
| **D. PrintWindow + PW_RENDERFULLCONTENT** | 无（系统 API） | ✅ | ✅（GDI 窗口） | ❌ | Vista+ | 否 | 否 |
| **E. mss** | pip 包 | ❌ 屏幕区域 | ❌ | ❌ | 老系统友好 | 否（可打包） | 否 |
| **F. OBS / 虚拟摄像头** | 需用户装 OBS | — | — | — | — | **要装** | ⚠️ 重 |
| **G. 内核态抓屏驱动** | 驱动 | — | — | ✅ | — | **要装驱动** | ❌ **禁止** |

### 6.2 关键判断

**B（DXGI Desktop Duplication）是最值得知道的选项，但不是兜底**：
它**就在 `windows-capture` 2.0.1 里**（实测 `dir()` 有 `DxgiDuplicationSession`，
README 也写了用法），**零新增依赖**。但它：
1. **只能按 `monitor_index` 抓整个显示器**，**不能抓单个窗口** —— 与项目「按 hwnd 抓」的设计冲突；
2. 同样依赖 D3D11（虚拟机/无硬件设备场景**一样失败**，见 luxstream-setup 原文）；
3. 玩家若把游戏窗口放在副屏、或窗口不全屏，就得自己裁剪 —— 且**多屏不同 DPI 时坐标换算会变复杂**。

**C / D（GDI 系）是唯一「老系统也能跑」的兜底**，但：
- **C（BitBlt 屏幕区域）会被遮挡**——`cua/capture.rs` 里专门写了 `target_is_obscured()`
  来检测这一点，注释原文："Without this signal, the BitBlt result is silently misleading
  （a backgrounded Notepad screenshot returned LibreOffice's pixels）"。
  对本项目而言：挂机时玩家很可能把游戏放后台看视频 → **画面全错且不报错**，比抓不到更糟。
- **D（PrintWindow）**对现代 GPU 直绘窗口（UWP / DirectComposition / 部分游戏）
  会返回**全黑**（`cua/capture.rs` 的 `is_mostly_black_bgra()` 就是为这个写的）。
  但有一个宝贵特性：**它在目标不可见/被遮挡时依然能拿到该窗口自己的画面**（GDI 后端窗口）。

⇒ **结论：不建议更换主方案。** WGC 已经是「不装驱动、不碰进程」前提下能力最强的选择。
GDI 系可以作为**最后兜底**，但必须配合「遮挡检测 + 全黑检测」，
否则会引入比现在更难查的静默错误。**这一步是否要做，需要拍板。**

### 6.3 一个纯收益的小改进（建议做）

`secondary_window`／`draw_border=False` 的补用（见 §5.5），零风险。
另外可考虑把 `tools/grab_frame.py` 的「8 秒等帧超时 + 逐条排除」逻辑
**下沉到 `GameWindowCapturor` / 引擎启动路径**，把 B 类静默失败变成**可读报错**。

## 七、给用户看的白话版（可直接用于 issue 回复 / 用户版文档）

> **为什么抓不到画面？**
>
> 本工具靠 Windows 自带的「抓窗口画面」功能工作。它对窗口状态比较挑：
>
> 1. **游戏窗口不能被最小化** —— 最小化后 Windows 就不再画它了，工具一帧都拿不到。
>    点任务栏把游戏还原就行。
> 2. **游戏必须是窗口模式**，不能是独占全屏。在游戏设置里改成「窗口」或「窗口化全屏」。
> 3. **窗口大小要和配置一致** —— 不一致时工具会弹窗，点「一键按当前窗口大小改配置」即可。
> 4. **游戏窗口被别的窗口挡住没关系**，最小化不行。
> 5. **系统要 Windows 10 1809 以上**。更老的系统用不了。
> 6. **不支持在虚拟机里跑**。因为虚拟机的虚拟显卡不提供抓屏所需的硬件加速。
>    如果你是在远程桌面里用，也可能抓不到，建议在本地物理机前运行。

## 八、尚待实测验证的（不要当结论用）

以下几条**本次没有条件实测**，标注为待验证，避免被当成定论：

1. **RDP 下 WGC 的实际行为** —— 依据第三方源码注释推断，未实机复现。
   `GetSystemMetrics(SM_REMOTESESSION)` 可用来先做检测，但**检测到 RDP 后是否必然失败，未验证**。
2. **虚拟机中的实际报错形态** —— 判断为 A 类（D3D11 设备创建失败抛异常）还是 B 类（静默），未实测。
3. **老核显（如 Intel HD 3000 级别）能否创建 FL11.0 设备** —— 未实测。
4. **玩家多屏不同 DPI 缩放时，`crop_frame_to_client` 的裁剪口径是否仍然成立** ——
   issue #2 用户是缩放非 100% 的多屏环境，**本机（缩放 100%）复现不了**。
   这是**下一轮最值得实测的方向**（可用「改显示器缩放 + 多屏」现场构造）。
5. **Unity 客户端在独占全屏/无边框窗口下的表现** —— 未实测。
