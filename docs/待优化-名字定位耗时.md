## 一、现象与数据（来自用户日志，非推测）

用户日志里这两行：

```
[16:07:56] [性能] 近5秒 fps=0.1（1帧）| 一帧 17285ms | 名字定位96(峰96) 小地图定位4 抓帧4

```

- **一帧 95ms ≈ 10fps**，而配置里主循环目标是 30fps（33ms/帧）
- **名字定位占 80ms**，是绝对大头（怪检测 16ms、小地图 3ms、抓帧 4ms）
- 注意第一行 `17285ms` 是**启动首帧**（含初始化），不是稳态值；要看第二行的 95ms

**影响**：10fps 仍能挂机，但反应迟钝（走位/打怪的节奏都比 30fps 差）。
**不是 bug**，是性能问题。

## 二、机制调研（已做，**含真机实测数据**）

名字定位走 `src/utils/common.py` 的 `find_pattern_sqdiff()`，它是**两级搜索**：

1. **局部**：以 `last_result`（上一帧位置）为中心 ±`local_search_radius`（默认 50px）搜
2. **全局回退**：局部得分不达标（> `global_diff_thres`）时，**退回全图搜**

### ★ 真机实测（2026-09-27，本机 RTX3070 + 真实游戏画面）

**素材**：真实游戏截图 `debug/capture_raw_2026-09-27_17-45-46.png`（1368×800，
地图「废都南方工地」，角色名 `Kumanva`），模板从画面里实抠。

| 路径 | 耗时 | 说明 |
|---|---|---|
| **局部命中**（last_result 正确） | **0.43 ~ 0.79 ms** | 稳态路径 ✅ |
| **全图回退** | **19.5 ~ 22.2 ms** | 局部失败时走这条 |
| **加速比** | **约 50 倍** | |

**局部搜索半径的影响**（实测）：

| 半径 | 耗时 |
|---|---|
| 30px | 0.20 ms |
| 50px（当前值） | 0.39 ms |
| 80px | 0.72 ms |
| 120px | 1.67 ms |

**局部命中能跟上的位移**（实测，把 last_result 故意偏移）：

| 偏移 | 局部是否命中 |
|---|---|
| 0 ~ 50px | ✅ 命中 |
| 60px 以上 | ❌ 落回全图 |

### ★ 80ms 的成因（找到了）

一次名字定位**不是只跑一次匹配**，而是最多跑 3 次（见 `get_player_location_by_nametag`）：

1. **主匹配**（整块，`split_width: 999`）
2. 主匹配不达标 → **兜底匹配**（切块 `split_width_fallback: 30`，分成 2 块）
3. 兜底还要分左右半，每块各算一次

而**每一次失败都会退回全图（约 20ms）**，所以最坏路径：

```
20ms（主匹配回退全图） + 20ms × 2（兜底两个切块，各自回退全图） ≈ 60ms
再加其它开销 → 与用户报的 80ms 量级一致 ✅
```

**结论**：用户那台机器上，名字定位**长期走失败路径**（名牌被盖住 / 匹配不上），
每次失败都付全图代价。本机稳态只要 0.5ms，说明**正常情况很快，慢是慢在失败路径**。

### 相关配置（`config_default.yaml`）

```yaml
nametag:
  diff_thres: 0.01          # 最终判定"命中"的阈值
  global_diff_thres: 0.01   # 局部搜索"够好"的阈值；达标就不再全图搜
  split_width: 999          # 主匹配用整块
  split_width_fallback: 30  # 兜底切块宽度（0 = 关闭兜底）
```

### 已排除的推断

一度怀疑「0.01 太严导致总是回退」，但**真机+合成数据都推翻了**：
真实模板对真实画面 score = **0.00000**（完美匹配），噪声 ±12 时也只有 0.0019，
都远低于 0.01。**阈值本身没问题，不要改它。**

## 三、优化方向（**已按真机数据重新排序**，均未实施）

### ★ A. 首选：失败路径的全图回退要**限流**（最直接、收益最大）

**问题**：一次定位最多 3 次匹配，**每次失败都回退全图（~20ms）** ⇒ 最坏 60~80ms。
但"失败"往往**不是真的位置变了**，而是名牌被别的玩家盖住、或那一帧画面异常 ——
这种情况下**位置其实没怎么动**，完全没必要每块都做全图搜索。

**方案**：失败路径也优先用局部（扩大半径或用上次结果），只在
「连续失败 N 帧」或「局部也找不到」时才做**一次**全图搜索，且**一次定位内最多全图搜一次**。

**预期**：最坏从 60~80ms 降到 20~25ms（因为全图只做一次而不是三次）。
**风险**：低 —— 只要保证"连续失败后仍会做全图"，正确性不降级。

### B. 局部搜索半径从 50 调大（低成本，配合 A 用）

实测：半径 50→0.39ms、80→0.72ms、120→1.67ms（**都远小于全图的 20ms**）。
而实测"局部能跟上的位移"边界正好在 **50px 附近，60px 就落回全图**。

**方案**：把 `local_search_radius` 从 50 提到 80 或 100。
**收益**：更大位移（被怪撞飞、快速走位）也能走便宜的局部路径。
**代价**：局部本身从 0.39 → 0.72~1.0ms（可忽略）。
**风险**：低。

### C. 中风险：降频（不必每帧定位）

代码注释里有项目自己的实测：「同一张地图角色屏幕位置几乎是死的
（连续 5 帧恒为 (711,382)，跨图也只有 y 差 39px）」。

**方案**：位置连续 K 帧无变化时自动降频；一旦变化立刻恢复满速。
**风险**：攻击框位置依赖它，降频会让打怪滞后。**需先在真机量化"位置变化速率"**再定。

### D. 已排除的：调阈值
`diff_thres` / `global_diff_thres` 的 0.01 **没问题**（真机实测 score=0.00000），
**不要动它**。
